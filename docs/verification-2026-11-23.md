# 로컬 DB 및 실제 브라우저 검증 — 2026-11-23

## 결과

Neon 스키마 생성 및 로컬 브라우저의 방 생성 → 참여자 3명 입력 → 실제 길찾기 기반 추천 → 카카오 지도 표시를 확인했다. 확인된 앱 결함은 없으며 앱 동작 코드는 이번 검증에서 변경하지 않았다. 배포 환경을 검증한 것은 아니다.

## DB 변경 및 재조회

- 먼저 `information_schema`를 조회: 연결된 DB의 `public` 테이블/컬럼은 0개였다.
- 현재 `src/lib/db/schema.ts`를 Drizzle로 SQL 생성 후 검토했다. 연결 정보는 Node `--env-file=.env.local`로만 로드했으며 출력하지 않았다.
- 비어 있음을 트랜잭션 안에서 다시 확인하고 `rooms`, `participants`, FK, 인덱스를 생성했다. DROP/TRUNCATE/기존 데이터 삭제는 실행하지 않았다.
- DB 재조회: rooms 4컬럼, participants 8컬럼, 양쪽 UUID 기본키, slug UNIQUE, room_id FK(`ON DELETE CASCADE`), `participants_room_id_idx` 확인.
- 임시 생성 SQL/스냅샷은 검토·적용 후 제거했다. 별도 Drizzle migration journal을 DB에 설치하지 않았다. 기존 테이블을 재생성하는 migrate가 아니라, README의 명시적 env 로딩 + push로 차이를 확인한다.
- 브라우저에서 만든 테스트 방 1개/참여자 3개는 삭제하지 않고 남겼다. 마지막 DB 조회에서도 전체 rooms=1, participants=3이었다.
- 방 slug/UUID는 공개 저장소에서 생략한다. slug 자체가 방 접근 권한이므로 실제 검증방 식별자는 DB에서만 확인한다.

## 호출량 보호 및 확인

- 결과 조회 전 `participants × candidates` 호출 구조와 페이지 수명주기를 확인했다.
- 대중교통 1명 + 자동차 2명, 최대 후보 5개로 1회 계산했다.
- 앱 소스를 바꾸지 않는 scratch 전용 Node fetch 래퍼로 TMAP 요청 시작을 최대 5회로 제한했다. 여러 프로세스에서도 원자적 슬롯 파일을 사용했다.
- 결과 계산 전 슬롯 0개/이벤트 없음, 계산 후 실제 TMAP HTTP 200 **5회**, 카카오 자동차 HTTP 200 **10회**, 차단 이벤트 **0회**를 확인했다. 나머지 브라우저 확인과 테스트/빌드 후에도 동일했다.
- 계정의 정확한 남은 일일 쿼터는 조회하지 않았다. 기존 약 2회 사용은 이전 인수인계 정보이며 이번 집계에 합산해 확정 잔량으로 표현하지 않는다.
- 앱에는 아직 영구 캐시/일일 할당량 차단이 없다. 결과를 다시 열면 최대 5개의 TMAP 추가 요청이 발생할 수 있다. 검증용 개발 서버는 검증 후 종료했고 포트 3000 리스너가 없음을 확인했다.
- `.env.local`, 보존된 ODsay 어댑터, 배포/결제 설정은 변경하지 않았다.

## 한계 및 도구 이슈

- 지도 표시/마커 확인은 성공했다. 추가 지도 드래그 시험은 브라우저 입력 드라이버 `Input.dispatchMouseEvent` 타임아웃으로 완료하지 못했다. 이후 DOM/스크린샷 조회는 정상 복구됐다. 이를 앱 결함으로 분류하지 않았다.
- 전체 최초 로드의 콘솔 로그를 사전 수집하지 못했다. 결과 화면 이후 설치한 window error/rejection 수집에는 오류가 없었지만 전체 콘솔 무오류의 증거로 확대 해석하지 않는다.
- 프로덕션 서버의 전체 플로우, 배포 도메인, 모바일/다른 브라우저, 재계산/다중 동시 사용자 부하, ODsay 실키 호출은 이번 범위가 아니다.
- 결과 API는 실제 경로를 중복 계산하므로 별도로 호출하지 않았다. 검증한 실제 추천 경로는 브라우저 결과 페이지의 서버 계산이다.
- 스키마 실행 첫 시도는 안전 검사 정규식이 정상 FK의 `ON DELETE CASCADE`도 삭제 SQL로 오인하여 DDL 전에 중단됐다. 파괴 명령이 아니라 허용된 4개 문장 형태를 확인한 뒤 적용했다. 실패 시도에서 DB 변경은 없었다.
