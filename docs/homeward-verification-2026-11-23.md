# 출발 + 귀가 왕복 계획 검증 — 2026-11-23

## 구현 계약

- 별도 출발지/귀가지 검색. 귀가지는 출발지가 기본이고, 귀가 수단은 출발 수단이 기본이며 각각 편집 가능하다.
- 각 후보마다 출발지 → 후보 / 후보 → 귀가지 방향을 따로 조회한다. 역방향 값을 복사하지 않는다.
- 개인별 왕복 합계의 최댓값을 최소화하고, 동점이면 전원의 왕복 합계가 작은 후보가 먼저다.
- 결과는 각 leg의 분·수단·추정 여부·사유와 개인 합계를 표시한다. 한 leg라도 추정이면 합계에 추정 포함을 표시한다.
- 실제 출발시각·종료시각·시간표·막차 예측은 하지 않는다. 제한된 후보 중 비교이며 전역 최적해 보장은 아니다.

## 실제 Neon 검증

- 변경 전 `information_schema.columns`와 기존 참여자 수 6을 읽었다.
- `scripts/homeward.sql`의 nullable 컬럼 4개만 additive 적용: `home_address_label`(varchar),
  `home_lat`/`home_lng`(double precision), `return_transport_mode`(varchar).
- 변경 후 컬럼·nullable 속성을 재조회. 기존 참여자 원본 필드 6행과 quota 내용이 완전히 같은지 비교했다.
- 공개 앱 폼으로 합성검증 A(강남 출발/왕십리 귀가), B(홍대 출발/동일 귀가) 제출 후
  공개 GET과 Neon에서 주소·좌표·각 수단을 재조회했다.
- 별도 합성 검증방에 자동차 출발/대중교통 귀가, 별도 주소·좌표를 POST하고 공개 GET 및 Neon에서 재조회.
  잘못된 귀가 경도 POST는 400, 참여자 수가 1명 그대로인지 재조회했다.
- 검증방 2개/합성 참여자 3개를 남겼다. 기존 데이터/운영 quota를 삭제하거나 초기화하지 않았다.

## 공개 배포 브라우저 검증

- production alias `https://thenext-eta.vercel.app`에서 인증 없는 HTTP 200, 최종 호스트 동일 확인.
- 실제 390px 모바일 viewport에서 방 생성 → 별도 출발/귀가 검색 → 독립 수단 토글 → 제출 → GET 재조회.
  기본 동일 귀가 제출도 검증했다. 폼/결과 모두 가로 스크롤 없음(390=scrollWidth).
- 순수 대중교통 두 참여자의 결과만 열었다. **rolling quota가 8회 소진 상태이고 모두 24시간 내임을 먼저 읽고**
  결과 후 동일 행 내용을 다시 비교했다. 자동차/대중교통 실제 길찾기 요청은 **0회**.
  별도 자동차 수단 저장 검증방에서는 결과를 열지 않았다. 장소 검색 요청과 DB 요청은 실제로 수행했다.
- 화면에 후보 3곳, 각 2명×2방향 = 12 leg, 각 시간/추정 사유/합계 표시 확인.
  서버 페이지 계산 후 결과 API가 `status: cached`로 같은 데이터를 반환했다.
- 실제 반환 후보의 `(개인 최대 왕복, 전원 왕복 합)`:
  삼각지역 `(50,94)`, 녹사평역 `(50,96)`, 숙대입구역 `(51,93)`.
  합계 산식, 최댓값, 동점 정렬, 모든 leg `estimateReason: quota`를 코드로 검증했다.
- 브라우저 결과 이동은 최초 tool 5초 제한을 넘겼으나, 재이동/재계산 없이 현재 DOM을 읽어 정상 완료를 확인했다.
